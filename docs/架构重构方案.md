# 架构重构方案：UI / Logic 彻底分离

> 目标：**核心逻辑脱离 Flutter 能独立运行**，UI 只负责渲染和交互。
>
> 本文档覆盖 `lib/` 全部四层，按依赖方向自底向上设计。

---

## 1. 现状诊断

### 1.1 当前依赖图

```
presentation/  ←── 依赖 ──  application/  ←── 依赖 ──  data/
                                        ←── 依赖 ──  core/
                                                      ↑
data/  ←── 依赖 ──  core/
```

**没有循环依赖。** 方向是对的。但问题出在**职责分配**：

### 1.2 ChatPage 做了太多不该做的事

`chat_page.dart`（426 行）当前承载的业务逻辑：

| 方法 | 行号 | 实际职责 | 应归属 |
|------|------|---------|--------|
| `_consumeDelta(AgentResponse)` | 168-183 | AgentResponse → Markdown 序列化 | application |
| `_appendDelta(turnId, delta)` | 188-207 | 流式消息落库判断(append vs appendDelta) | application |
| `_finalizeTurn(turnId)` | 210-218 | 流式终结 + bumpRound | application |
| `_send(userInput)` 编排部分 | 100-158 | turnId 生成、Agent 订阅、落库回调 | application |
| `_runToken` 识别孤儿 run | 128-132 | 并发保护 | application |
| `SendStatus` 状态机 | 93-96 | 发送状态管理 | application |

**ChatPage 真正该做的**（只有这些）：
- `build()` / `_renderList()` — 渲染
- `_scrollToBottom()` — UI 操作
- `_showError()` / `_confirmClear()` / `_showMetaSheet()` — 交互

### 1.3 ConversationService 太薄

当前 `ConversationService` 只是一个「Session CRUD + runAgent 转发 + 起名」的门面，核心编排逻辑全在 ChatPage。

### 1.4 多会话并行无保障

`_activeSub` / `_activeTurnId` 是 Page 字段。用户切到 B 会话发消息，A 会话的订阅被覆盖，run_A 后续事件无人收（虽然 DB watch 还在工作，但状态管理是乱的）。

## 2. 目标架构

### 2.1 四层定义

```
┌──────────────────────────────────────────────────┐
│  core/  ← 纯领域逻辑，零外部依赖                   │
│  Agent、Tool、Model、Util                         │
│  可在任何 Dart 环境运行（CLI / test / server）      │
└──────────────────────────────────────────────────┘
                       ↑
┌──────────────────────────────────────────────────┐
│  data/  ← 持久化 + 基础设施                        │
│  Drift DB、Repository 实现、Tool 实现               │
│  依赖 core/ 抽象接口，不依赖 application/presentation│
└──────────────────────────────────────────────────┘
                       ↑
┌──────────────────────────────────────────────────┐
│  application/  ← 业务编排，纯 Dart                  │
│  业务状态管理、Agent → Message 翻译、                │
│  流式消息生命周期、多会话并发控制                     │
│  不依赖 Flutter widget，不 import flutter_*         │
│  可用 dart test 独立测试                            │
└──────────────────────────────────────────────────┘
                       ↑
┌──────────────────────────────────────────────────┐
│  presentation/  ← Flutter UI                      │
│  只做：渲染 + 交互 + 调用 application 层             │
│  零业务逻辑，零 DB 操作                             │
└──────────────────────────────────────────────────┘
```

### 2.2 核心原则

1. **application 层不 import flutter_** — 业务逻辑可在纯 Dart VM 跑
2. **presentation 层不 import data/** — UI 只通过 application 操作数据
3. **core/ 不 import data/ 或 application/** — 纯领域模型 + 抽象接口
4. **providers.dart 是桥接层** — 它 import data/ 实现，暴露为 Riverpod Provider 供 UI 消费

### 3.1 新增 `application/agent/orchestrator.dart` — Agent 运行协调器

**这是本次重构的核心。** 职责：接管 ChatPage 里所有 Agent 运行编排逻辑。

```dart
// application/agent/orchestrator.dart

/// 单次 run 的状态
class AgentRunState {
  final String conversationId;
  final String turnId;
  final SendStatus status;         // idle / sending / error
  final String? errorMessage;
  // ... 不含 UI 状态
}

enum SendStatus { idle, sending, error }

/// Agent 运行协调器：管理 run 生命周期 + 消息落库
/// 每个 conversationId 一个实例，通过 Map 管理多会话并行
class AgentOrchestrator {
  final Agent _agent;
  final SessionNameAgent _sessionNameAgent;
  final MessageRepository _messageRepo;
  final SessionRepository _sessionRepo;
  final ConfigRepository _configRepo;

  // 多会话并行：Map<conversationId, _RunSession>
  final Map<String, _RunSession> _activeRuns = {};

  // 对外暴露的事件流
  final _runStatesController = StreamController<AgentRunState>.broadcast();
  Stream<AgentRunState> get runStates => _runStatesController.stream;

  /// 启动一次 Agent 运行（会检查并发：同会话不能同时跑两个）
  Future<void> send({
    required String conversationId,
    required String userInput,
  }) async { ... }

  /// 取消当前 run
  void cancel(String conversationId) { ... }

  /// 重试（复用上一次的 userInput）
  Future<void> retry(String conversationId) async { ... }
}
```

**内部 _RunSession 的关键逻辑**（从 ChatPage._send 搬过来）：

```dart
class _RunSession {
  final String turnId;
  String? _lastUserInput;  // 用于 retry
  AgentSubscription? _subscription;

  void subscribe() {
    _lastUserInput = ...;  // 从 DB 读最后一条 user message
    final run = _agent.run(...);
    _subscription = run.subscribe()
      .doOnEach((response) {
        // 1. AgentResponse → Markdown 序列化（见 3.2）
        final markdown = AgentResponseSerializer.serialize(response);

        // 2. 落库
        final existingMsg = _messageRepo.findById('assistant-$turnId');
        if (existingMsg == null) {
          _messageRepo.append(Message(
            conversationId: ...,
            role: MessageRole.assistant,
            content: markdown,
            type: MessageType.text,
            turnId: turnId,
            streaming: true,
          ));
        } else {
          _messageRepo.appendDelta('assistant-$turnId', markdown);
        }
      })
      .doOnComplete(() {
        _messageRepo.finalize('assistant-$turnId');
        _messageRepo.bumpRound(conversationId);
      })
      .doOnError((error) { ... })
      .doFinally((signal) {
        _activeRuns.remove(conversationId);
        _runStatesController.add(AgentRunState(...));
      });
  }
}
```

### 3.2 新增 `application/agent/response_serializer.dart` — AgentResponse → Markdown

从 ChatPage._consumeDelta 搬出来，变成可独立测试的纯函数：

```dart
// application/agent/response_serializer.dart
// 纯 Dart，零依赖

class AgentResponseSerializer {
  /// 将 AgentResponse 序列化为可追加的 Markdown 字符串
  static String serialize(AgentResponse response) {
    return switch (response) {
      AgentThinking(:final text) => '<think>$text</think>',
      AgentText(:final text) => text,
      AgentToolCall(:final name, :final args, :final callId) =>
        '\n\n:::tool_call id="$callId" name="$name"\n'
        '```json\n${jsonEncode(args)}\n```\n:::\n\n',
      AgentToolResult(:final output, :final callId) =>
        '\n\n:::tool_result id="$callId"\n$output\n:::\n\n',
      AgentFinish() => '',
    };
  }
}
```

### 3.6 重构 `providers.dart` — 桥接层

新增 Provider 替换当前在 ChatPage 里做的编排：

```dart
// application 层的 AgentOrchestrator 通过 Provider 暴露
final agentOrchestratorProvider = FutureProvider<AgentOrchestrator>((ref) async {
  final agent = await ref.watch(quickAgentProvider.future);
  final sessionNameAgent = await ref.watch(sessionNameAgentProvider.future);
  final messageRepo = await ref.watch(messageRepositoryProvider.future);
  final sessionRepo = await ref.watch(sessionRepositoryProvider.future);
  final configRepo = await ref.watch(configRepositoryProvider.future);

  return AgentOrchestrator(
    agent: agent,
    sessionNameAgent: sessionNameAgent,
    messageRepo: messageRepo,
    sessionRepo: sessionRepo,
    configRepo: configRepo,
  );
});

// 多会话并行的 run 状态
final runStateProvider = StreamProvider.family<AgentRunState, String>(
  (ref, conversationId) async* {
    final orchestrator = await ref.watch(agentOrchestratorProvider.future);
    yield* orchestrator.runStates
        .where((state) => state.conversationId == conversationId);
  },
);

// 单个会话的消息流（替代 ChatPage 内部 _messages 列表）
final conversationMessagesProvider = StreamProvider.family<List<Message>, String>(
  (ref, conversationId) async* {
    final repo = await ref.watch(messageRepositoryProvider.future);
    yield* repo.watch(conversationId);
  },
);
```

## 4. 多会话并行支持

### 4.1 设计

```
AgentOrchestrator._activeRuns: Map<String, _RunSession>
                                  ↓
                           conversationId
                                  ↓
                   每个会话独立的 AgentSubscription + turnId
```

- 用户在 A 发消息 → 创建 `_RunSession('conv-A', turnId='t-xxx')`
- 切到 B 发消息 → 创建 `_RunSession('conv-B', turnId='t-yyy')`
- A 和 B 各自独立订阅 Agent 流，互不干扰
- 再次在 A 发消息 → 检查 `_activeRuns['conv-A']` 是否还在跑，是则 ignore

### 4.2 并发策略

同一会话同一时间**只允许一个 run**。第二次发送被 ignore（UI 显示"上一个还没完成"）。

### 4.3 Page 退出不影响 run

AgentOrchestrator 持有 run 状态，Page 退出只是不再 watch stream。run 继续跑，DB 继续写。下次进 Page，重新 watch 即可拿到最新状态。

## 9. 风险评估

| 风险 | 影响 | 缓解 |
|------|------|------|
| Phase 3 改动大，可能引入 bug | 中 | Phase 1-2 先打好基础，逐步替换 |
| Orchestrator 的并发控制可能漏 edge case | 低 | 同会话只允许一个 run，策略简单 |
| Provider 依赖链变动导致初始化顺序问题 | 低 | `FutureProvider` 天然保证顺序 |
| 消息列表从 `setState` 改为 `StreamProvider`，可能有时序差异 | 中 | 确保 DB watch 在 run 状态之前 emit |
